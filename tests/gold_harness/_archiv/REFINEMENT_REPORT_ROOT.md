# Gold-vs-Silver Harness Refinement Report

Date: 2026-09-16
Scope: Phase 2–5 implementation completed; Phase 6 fix loop not yet started.

## 1. What was refined

### Silver JSON dump (`examples/dwg2json.rs`)
- Reads a DWG into `CadDocument`, serializes the document with `serde`, and
  re-injects the 12 serde-skipped `EntityCommon` round-trip fields under a
  `_common_dwg` map keyed by entity handle.
- Fields re-injected: `linetype_handle`, `graphic_data`, `color_book_handle`,
  `face_visual_style_handle`, `edge_visual_style_handle`, `material_flags`,
  `material_handle`, `shadow_flags`, `plotstyle_flags`, `plotstyle_handle`,
  `entity_mode`, `has_ds_data`.

### Silver rewrite binary (`examples/dwgrewrite.rs`)
- Minimal read → write binary that targets the same DWG version as the source.

### Normalizers (`tests/gold_harness/normalize_gold.py`, `normalize_silver.py`)
- **Gold normalizer** keeps only the top-level `OBJECTS` array, drops all header
  and section metadata, and flattens points / handles / colors to a canonical
  shape.
- **Silver normalizer** now emits:
  - every `entities` entry,
  - every `objects` entry,
  - every table record (layers, linetypes, text styles, block records, dim
    styles, app ids, views, vports, UCSs).
- Resolves entity layer **names** to layer **handles** using the silver
  `layers.entries` table, so `layer` becomes comparable to gold's handle.
- Maps `EntityType` / `ObjectType` variant names to gold type names and applies
  per-type field-name remaps (e.g. `normal` → `extrusion`, `start_point` →
  `start_pt`).

### Differ (`tests/gold_harness/diff_fields.py`)
- Aligns records across gold and silver by `(type, ordinal-within-type)`, not
  by raw handle, because handles are reassigned on rewrite.
- For handle-valued fields, compares the **resolved target type** (via a
  handle-value → type map built independently per side), not the raw handle id.
- Reports `missing_in_silver`, `wrong_value`, `extra_in_silver`, and
  `count_mismatch`.

### Driver / batch / cargo test
- `run_roundtrip.py` orchestrates the three diffs per file.
- `run_corpus.py` runs the driver over the in-scope corpus and aggregates a
  ranked report.
- `tests/gold_roundtrip.rs` is gated behind the `gold-harness` feature and
  shells out to the Python driver; strict zero-`missing_in_silver` mode is
  opt-in via `GOLD_HARNESS_STRICT=1`.

## 3. Handle comparison design and alternatives

### Problem
LibreDWG emits handles as integer ids (e.g. `layer: [5,1,16,16]`). cadcodec
serde emits handles as integer ids too. On a rewrite, cadcodec assigns **new**
handle ids, so raw ids cannot be compared directly between `gold_orig` and
`gold_rt`, or between gold and silver.

### Chosen design
1. **Alignment by `(type, ordinal)`**: the differ groups records by type and
   pairs the first gold `LINE` with the first silver `LINE`, etc. This is the
   plan's stated rule and works for all tested files.
2. **Handle-valued field comparison by resolved target type**: before diffing,
   the differ builds a map `handle_value → record_type` on each side
   independently. When comparing a handle-valued field (e.g. `layer`,
   `ownerhandle`), it replaces the raw id with the type of the object that id
   points to. If both sides point to a `LAYER`, the field matches; if one
   points to a `LAYER` and the other to a `BLOCK_RECORD`, it is reported as a
   wrong value.

### Alternatives considered
- **Compare raw handle ids**: rejected because handles are intentionally
  reassigned by cadcodec's writer and would produce false positives on every
  roundtrip.
- **Use the silver `entity_index` / gold `handle` to align 1:1**: rejected
  because handles are not stable across read→write→read, and silver's
  `entity_index` is keyed by the silver-assigned id.
- **Normalize handles to symbolic names (e.g. "layer 0", "model space")**: too
  brittle; the chosen type-resolved approach is deterministic and matches the
  plan's wording.
- **Ignore all handle-valued fields**: rejected because handle topology (which
  type an entity owns/points to) is part of the "non-header structure" the loop
  must preserve.

### Known limitation
The current handle resolver cannot distinguish two objects of the **same**
type that are both valid targets. For example, if a `LINE` points to layer
handle 16 (layer "0") and a rewritten `LINE` points to layer handle 99
(layer "0"), both resolve to `LAYER` and match. This is acceptable for the
loop's convergence target because layer identity is semantically preserved;
if cadcodec swapped it to a different layer, the resolved type could still
match and the diff would miss it. A future improvement could resolve handles to
`(type, name)` when a name table is available.

## 4. Current baseline on `2000/Line.dwg`

After refinement and ignore-field tuning:
- **Read-fidelity diffs**: 2658
- **Entity-level diffs are small**: `LINE` has 9 diffs, all in
  `EntityCommon` skipped fields (`prev_entity`, `next_entity`, `nolinks`,
  `ltype_flags`, `plotstyle_flags`, `z_is_zero`) plus a few extra fields
  (`linetype`, `color_name`, `ownerhandle`).
- **Object-level diffs dominate**: `XRECORD`, `DICTIONARY`, `SCALE`,
  `VISUALSTYLE` representation mismatches. Many are silver-specific fields
  (e.g. `cloning_flags`, `is_temporary`) that do not exist in gold, or gold
  fields that silver does not store. These need per-object mapping work if
  they are to enter the fix loop.

## 5. Recommendations before Phase 6

1. **Freeze `ignore_fields.toml` now** and do not edit it during the loop.
2. **Scope the first fix-loop pass to entity `EntityCommon` fields**:
   `prev_entity`, `next_entity`, `nolinks`, `ltype_flags`, `plotstyle_flags`,
   `z_is_zero`. These are stored nowhere in cadcodec today and are exactly the
   kind of round-trip-only fields the plan targeted.
3. **Defer polyline vertex expansion** until a polyline fixture is actively
   processed.
4. **Defer full object topology fixes** (DICTIONARY, XRECORD, VISUALSTYLE,
   SCALE) unless they appear in the covered corpus as blockers for a covered
   entity type; otherwise mark them out-of-loop for now.
5. **Add `2000/Circle.dwg` to the regression test** as the next representative fixture. It exercises a different entity type and will reveal whether the `EntityCommon` field handling generalizes beyond `LINE`.
6. **Keep `GOLD_HARNESS_STRICT=1` opt-in** until the expanded corpus passes zero `missing_in_silver`.
